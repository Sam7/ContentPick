# Package distribution requirements

**Research checked:** 2026-10-09. Official-source links below were checked against the current project documentation on that date; package-manager policies can change, so recheck before submission.

This is a compatibility brief for roadmap M5.5/M5.6, not evidence that ContextPick currently produces acceptable packages or has been accepted by any repository. These public community channels do not require a paid app-store listing. Validate all installer-specific details against the actual release artifacts. Official repositories review and may decline submissions even when documented criteria appear satisfied.

## Windows Package Manager (WinGet community repository)

- **Artifact:** Community submissions accept MSIX, MSI, APPX, MSIXBundle, APPXBundle, or installer EXE; script-based installers are not accepted. Match the manifest architecture to the installed binaries. A normal Windows installer is the likely format to assess, but confirm the actual Tauri bundle, install scope, upgrade/uninstall behavior, and WebView2 prerequisites before choosing it. [Repository overview](https://github.com/microsoft/winget-pkgs) · [manifest installer schema](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.28.0/installer.md)
- **Manifest:** Submit a multi-file YAML set for one package version: version, installer, and default-locale manifests, with schema headers and matching package identifier/version/path. Include required identity and installer data, notably package name, publisher, version, license, installer type, architecture, direct installer URL and SHA-256. Locale metadata includes the user-facing name, publisher, and description; add official homepage/package URLs and other accurate optional metadata as appropriate. The current schema is authoritative for exact required fields. [Authoring/testing/submission guide](https://github.com/microsoft/winget-pkgs/blob/master/doc/README.md) · [installer schema](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.28.0/installer.md)
- **Hosting and integrity:** Installer URLs must be reachable over HTTPS by Microsoft validation and should resolve to an official publisher download source, not an unendorsed mirror, shortener, or gated URL. Pin the exact release artifact and record its SHA-256; validation downloads the installer and compares the digest. Do not replace bytes at an existing version URL. [Validation rules](https://github.com/microsoft/winget-pkgs/blob/master/doc/Validation.md)
- **Install behavior and signing:** The community repository requires packages to support both `silent` and `silentWithProgress` modes. Declare the supported modes and correct switches for the actual installer; validation must complete an unattended install in a clean standard-user environment. Test the real modes and dependency behavior. The community repository specifically requires MSIX packages to be signed. The cited repository/schema does not state an equivalent mandatory signature rule for EXE/MSI; signing those remains a release-security and user-trust goal, not a WinGet acceptance claim. [Installer schema](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.28.0/installer.md) · [validation stages](https://github.com/microsoft/winget-pkgs/blob/master/doc/Validation.md)
- **Submission and maintenance:** Run `winget validate --manifest …` and install from the local manifest; Windows Sandbox testing is also documented. Submit one package/version manifest set per PR to `microsoft/winget-pkgs`, respond to bot/moderator feedback, and keep future version updates aligned with immutable release artifacts and new hashes. A PR triggers automated manifest, URL, policy, and binary validation; a Microsoft/community review and applicable CLA process may apply. [Repository guide](https://github.com/microsoft/winget-pkgs/blob/master/doc/README.md) · [validation](https://github.com/microsoft/winget-pkgs/blob/master/doc/Validation.md) · [contributing/CLA](https://github.com/microsoft/winget-pkgs/blob/master/CONTRIBUTING.md)

## Chocolatey Community Repository

- **Artifact/package:** Publish a NuGet-format `.nupkg` containing a `.nuspec` and, as needed, `tools/chocolateyInstall.ps1`, uninstall script, and verification/license files. The nuspec carries package ID/version, title, authors/owners, project URL, license URL, summary/description, and dependencies/tags as applicable. For an installer-backed package, the install script must use the actual installer’s supported silent switches and handle exit codes; test upgrade and uninstall too. [Package creation](https://docs.chocolatey.org/en-us/create/create-packages/) · [community quick start](https://docs.chocolatey.org/en-us/create/create-packages-quick-start/)
- **Hosting and integrity:** Prefer a package script that downloads the exact installer from an official, stable HTTPS release URL rather than embedding binaries unless redistribution rights are clear. Use SHA-256 checksum validation in download helpers. Chocolatey’s published CPMR0027 rule is marked a requirement, but its page is currently a stub and says the validator implementation is pending; verify current review guidance when packaging. Do not depend on mutable “latest” bytes without a trustworthy version/hash strategy. If binaries are embedded in the package, the community validator requires both `LICENSE.txt` and `VERIFICATION.txt`/recognized equivalents; a license URL alone is insufficient. [Validator rules](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/) · [CPMR0027 status](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/cpmr0027/) · [embedded binary license requirement](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/cpmr0005/) · [embedded binary verification requirement](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/cpmr0006/) · [download helper](https://docs.chocolatey.org/en-us/create/functions/install-chocolateypackage/)
- **Metadata and rights:** Community nuspec metadata must identify the project, contain a meaningful description, and include the applicable license URL. Confirm legal rights to redistribute any binaries included in the `.nupkg`; a download-and-install package avoids embedding the app but still must point at the legitimate upstream artifact. [Moderation requirements](https://docs.chocolatey.org/en-us/community-repository/moderation/) · [package creation/redistribution guidance](https://docs.chocolatey.org/en-us/create/create-packages/)
- **Signing/platform policy:** The cited community package requirements do not establish code signing as a universal package acceptance prerequisite. Authenticode-signing the Windows installer is good release practice and should be represented truthfully in package metadata/release notes; never imply a signature exists until verified. Chocolatey’s package checksum and package review are separate from an installer’s Authenticode signature.
- **Submission and maintenance:** Build with `choco pack`, test installation from a local source (preferably a clean VM), verify silent install, upgrade and uninstall, then push the `.nupkg` to `https://push.chocolatey.org/` with a Chocolatey account/API key. New versions go through automated validation/verification and human moderation before approval; maintainers must respond to review and keep versions working as upstream URLs/releases change. Do not expose API keys in source or CI logs. [Quick start/push](https://docs.chocolatey.org/en-us/create/create-packages-quick-start/) · [moderation lifecycle](https://docs.chocolatey.org/en-us/community-repository/moderation/) · [push command](https://docs.chocolatey.org/en-us/create/commands/push/)

## Homebrew Cask (official macOS cask tap)

Homebrew is the recommended free macOS package-manager route for this desktop app. The official `homebrew/cask` tap is more discoverable, but admission is subject to its public-interest policy.

- **Artifact:** Casks distribute upstream-built macOS apps/installers. Provide a downloadable `.dmg`, `.zip`, `.pkg`, or other supported archive containing the app; a `pkg` installation needs an explicit `uninstall` stanza. The Cask uses a unique token/filename and structured Ruby DSL. [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook) · [acceptable casks](https://docs.brew.sh/Acceptable-Casks)
- **Cask metadata:** Required stanzas are `version`, `sha256`, `url`, `name`, `desc`, and `homepage`, plus the applicable artifact stanza such as `app` or `pkg`. Use a concrete version and exact SHA-256 for stable releases. `:latest`/`:no_check` are supported special values but weaken pinning and should not be selected without an explicit update/integrity rationale. Use `livecheck` where version discovery is non-obvious; provide architecture-specific URLs/checksums only if upstream actually publishes distinct artifacts. [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook)
- **Hosting and integrity:** The URL must deliver a release published by ContextPick or a distribution source the project publicly endorses; hidden/account-gated downloads and unendorsed mirrors are not acceptable. Keep a stable, publicly reachable release URL for each version and verify that its bytes match the cask SHA-256. Homebrew’s cask repository retains the formula metadata, not an uploaded app binary. [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks) · [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook)
- **Signing/notarization:** Homebrew’s cask acceptance policy requires macOS executable artifacts assessable by Gatekeeper to pass Homebrew’s Gatekeeper checks on a default macOS configuration; users’ Gatekeeper protections must not be disabled or bypassed. Homebrew applies quarantine and delegates those checks to macOS. Separately, Apple says apps distributed outside the Mac App Store are checked for Developer ID signing and, by default on current macOS, notarization. Plan a Developer ID signed and notarized app/package (and staple where supported), then verify on a clean supported Mac; this is the practical route to satisfy both Gatekeeper and friction-free installs. Treat Homebrew Gatekeeper acceptance as repository policy and signing/notarization as Apple platform behavior, not a Homebrew claim that notarization certifies safety. [Homebrew security model](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain) · [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks) · [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) · [Apple safe app guidance](https://support.apple.com/en-us/102445)
- **Submission and maintenance:** Read the acceptance policies, run applicable local cask audit/tests, fork `Homebrew/homebrew-cask`, and open a PR; official-tap changes are human reviewed. The shared policy currently expects public interest beyond the author (normally at least 30 forks, 30 watchers, or 75 stars; for a repository-owner self-submission, 90 forks, 90 watchers, or 225 stars), with exceptions at maintainers’ discretion. A live repository check on 2026-10-09 found 0 stars, 0 forks and 0 watchers, below the normal thresholds; do not assume an official cask PR will be accepted yet. A project-maintained third-party tap is a free fallback, but Homebrew treats third-party taps as unsupported code that requires explicit trust, so document that install step and limitation. A new cask creates ongoing maintenance obligations: keep versions/checksums/downloads current, respond to CI/review, and maintain a working supported macOS artifact. [Package acceptance policy](https://docs.brew.sh/Package-Acceptance-Policy) · [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks) · [open a Homebrew PR](https://docs.brew.sh/How-To-Open-a-Homebrew-Pull-Request) · [Homebrew security/review](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain)

## Roadmap mapping

The execution checklist remains in [ROADMAP](ROADMAP.md). M5.5 covers unpublished candidate bundles, local app installation tests and static/local package-definition validation. M5.6 covers immutable public release URLs, exact remote-asset validation, package submissions and accepted-channel installation. Package-manager PRs/submissions are separate external publications; only the Windows GitHub release was explicitly authorized on 2026-10-09.

For the generated Windows bundle, verify its installer type, architecture, scope, silent and silent-with-progress switches, WebView2 bootstrapper, upgrade/uninstall behavior and ARP identity. Confirm Authenticode status from the actual artifact. The Chocolatey package must have checksum-enforcing download scripts and valid metadata; if it embeds binaries, include recognized verification/license files and establish redistribution rights. For macOS, test the actual app/archive/installer and uninstall behavior on a supported Mac, check Gatekeeper on a default configuration, and record Developer ID signing/notarization. Validate manifests locally in M5.5, then against exact public HTTPS assets in M5.6. Keep API keys and signing credentials in authorized secret storage and document channel ownership, update monitoring, review response and package withdrawal.
