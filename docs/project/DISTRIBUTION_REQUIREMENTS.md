# Package distribution requirements

**Research checked:** 2026-10-09. Official-source links below were checked against the current project documentation on that date; package-manager policies can change, so recheck before submission.

This is a compatibility brief for roadmap M5.5/M5.6, not evidence that ContextPick currently produces acceptable packages or has been accepted by any repository. These public community channels do not require a paid app-store listing. Validate all installer-specific details against the actual release artifacts. Official repositories review and may decline submissions even when documented criteria appear satisfied.

## Precedent: Whisper Desk v0.1.0

The [Chocolatey package page](https://community.chocolatey.org/packages/whisperdesk/0.1.0) shows automated validation passing while verification failed and moderation is waiting for maintainer corrective action. Its [verifier report](https://gist.github.com/choco-bot/df5df32eb08ebd0bb0144f4bf334bc03) records a successful installer download and SHA-256 check, followed by the silent installer exiting with code 1 on Windows Server 2019 build 17763 on 1 October 2026. The report suggests a possible silent-install hang, but does not establish the cause. Whisper Desk's installer declares Windows 11 build 22000 as its minimum, so verifier incompatibility is plausible, not confirmed ([tagged installer source](https://github.com/Sam7/whisper-desk/blob/v0.1.0/packaging/windows/WhisperDesk.iss)). Chocolatey's published [verifier profile](https://docs.chocolatey.org/en-us/community-repository/moderation/package-verifier/) lists Windows Server 2019, WSL, .NET 3.5/4.8 and updates through 2024-05-28, with a 20-minute limit for each install/uninstall command. Treat that as the documented baseline, verify the actual image and limits before submission, and do not weaken ContextPick's real OS support to match it.

Whisper Desk's installer also downloads about 1.62 GB in CPU mode or 3.44 GB with GPU files, then prepares the runtime and runs inference checks. For ContextPick, document only its actual prerequisites and test installer network, disk/time/resource use, prompts and cleanup effects against the distributor limits.

The successful [recovery workflow](https://github.com/Sam7/whisper-desk/actions/runs/36683319773) published the [GitHub release](https://github.com/Sam7/whisper-desk/releases/tag/v0.1.0) and submitted the [Chocolatey package](https://community.chocolatey.org/packages/whisperdesk/0.1.0), yet logged that initial WinGet registration was still required. This is evidence that CI success, a release and package submission do not establish distributor acceptance or availability. The package page and [initial WinGet submission instructions](https://github.com/Sam7/whisper-desk/blob/main/packaging/winget/bootstrap/README.md) provide the separate moderation and registration trail.

This review found no published `DotSam.WhisperDesk` manifest or matching PR; the release log says the first reviewed submission remained outstanding. That indicates the initial submission had not been evidenced here, not that Microsoft rejected it.

## Windows Package Manager (WinGet community repository)

- **Artifact:** Community submissions accept MSIX, MSI, APPX, MSIXBundle, APPXBundle, or installer EXE; script-based installers are not accepted. Match the manifest architecture to the installed binaries. A normal Windows installer is the likely format to assess, but confirm the actual Tauri bundle, install scope, upgrade/uninstall behavior, and WebView2 prerequisites before choosing it. [Repository overview](https://github.com/microsoft/winget-pkgs) · [manifest installer schema](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.28.0/installer.md)
- **Manifest:** Submit a multi-file YAML set for one package version: version, installer, and default-locale manifests, with schema headers and matching package identifier/version/path. Include required identity and installer data, notably package name, publisher, version, license, installer type, architecture, direct installer URL and SHA-256. Locale metadata includes the user-facing name, publisher, and description; add official homepage/package URLs and other accurate optional metadata as appropriate. The current schema is authoritative for exact required fields; use the schema version recommended in the repository's current PR guidance, not simply the highest numbered schema. The repository's manifest instructions currently recommend 1.12.0 and also support 1.10.0; recheck the current guidance at submission. [Authoring/testing/submission guide](https://github.com/microsoft/winget-pkgs/blob/master/doc/README.md) · [repository manifest instructions](https://github.com/microsoft/winget-pkgs/blob/master/.github/instructions/manifests.instructions.md) · [installer schema](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.28.0/installer.md)
- **Hosting and integrity:** Installer URLs must be reachable over HTTPS by Microsoft validation and should resolve to an official publisher download source, not an unendorsed mirror, shortener, or gated URL. Pin the exact release artifact and record its SHA-256; validation downloads the installer and compares the digest. Do not replace bytes at an existing version URL. [Validation rules](https://github.com/microsoft/winget-pkgs/blob/master/doc/Validation.md)
- **Install behavior and signing:** The community repository requires packages to support both `silent` and `silentWithProgress` modes. Declare the supported modes and correct switches for the actual installer; validation must complete an unattended install in a clean standard-user environment. Test the real modes and dependency behavior. The community repository specifically requires MSIX packages to be signed. The cited repository/schema does not state an equivalent mandatory signature rule for EXE/MSI; signing those remains a release-security and user-trust goal, not a WinGet acceptance claim. [Installer schema](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.28.0/installer.md) · [validation stages](https://github.com/microsoft/winget-pkgs/blob/master/doc/Validation.md)
- **Initial submission and maintenance:** For a new ID, create and submit the complete first-version manifest set as a one-time PR. Track the PR through validation, moderator approval, merge and successful repository publication before calling the ID registered or installable. Routine update automation applies only after registration; a generated manifest, warning followed by a successful CI exit, or submitted PR does not satisfy this gate. For every version, retain the PR/check results and verify `winget install` from the published source on a clean machine. [First-contribution checklist](https://github.com/microsoft/winget-pkgs/blob/master/doc/FirstContribution.md) · [repository guide](https://github.com/microsoft/winget-pkgs/blob/master/doc/README.md) · [validation and publication lifecycle](https://github.com/microsoft/winget-pkgs/blob/master/doc/Validation.md) · [contributing/CLA](https://github.com/microsoft/winget-pkgs/blob/master/CONTRIBUTING.md)

## Chocolatey Community Repository

- **Artifact/package:** Publish a NuGet-format `.nupkg` containing a `.nuspec` and, as needed, `tools/chocolateyInstall.ps1`, uninstall script, and verification/license files. The nuspec carries package ID/version, title, authors/owners, project URL, license URL, summary/description, and dependencies/tags as applicable. For an installer-backed package, the install script must use the actual installer’s supported silent switches and handle exit codes; test upgrade and uninstall too. [Package creation](https://docs.chocolatey.org/en-us/create/create-packages/) · [community quick start](https://docs.chocolatey.org/en-us/create/create-packages-quick-start/)
- **Hosting and integrity:** Prefer a package script that downloads the exact installer from an official, stable HTTPS release URL rather than embedding binaries unless redistribution rights are clear. Use SHA-256 checksum validation in download helpers. Chocolatey’s published CPMR0027 rule is marked a requirement, but its page is currently a stub and says the validator implementation is pending; verify current review guidance when packaging. Do not depend on mutable “latest” bytes without a trustworthy version/hash strategy. If binaries are embedded in the package, the community validator requires both `LICENSE.txt` and `VERIFICATION.txt`/recognized equivalents; a license URL alone is insufficient. [Validator rules](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/) · [CPMR0027 status](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/cpmr0027/) · [embedded binary license requirement](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/cpmr0005/) · [embedded binary verification requirement](https://docs.chocolatey.org/en-us/community-repository/moderation/package-validator/rules/cpmr0006/) · [download helper](https://docs.chocolatey.org/en-us/create/functions/install-chocolateypackage/)
- **Metadata and rights:** Community nuspec metadata must identify the project, contain a meaningful description, and include the applicable license URL. Confirm legal rights to redistribute any binaries included in the `.nupkg`; a download-and-install package avoids embedding the app but still must point at the legitimate upstream artifact. [Moderation requirements](https://docs.chocolatey.org/en-us/community-repository/moderation/) · [package creation/redistribution guidance](https://docs.chocolatey.org/en-us/create/create-packages/)
- **Signing/platform policy:** The cited community package requirements do not establish code signing as a universal package acceptance prerequisite. Authenticode-signing the Windows installer is good release practice and should be represented truthfully in package metadata/release notes; never imply a signature exists until verified. Chocolatey’s package checksum and package review are separate from an installer’s Authenticode signature.
- **Initial submission and maintenance:** Push the first `.nupkg` with `choco push`; track it through package validation, independent install/upgrade/uninstall verification and human moderation. A successful push, local-source test or validator result is not approval. Treat the channel as available only when the package page shows **Approved** and a clean `choco install` from the Community Repository installs the recorded version. Do not expose API keys in source or CI logs. [Quick start/push](https://docs.chocolatey.org/en-us/create/create-packages-quick-start/) · [moderation lifecycle](https://docs.chocolatey.org/en-us/community-repository/moderation/) · [verifier environment, tests and bypass request](https://docs.chocolatey.org/en-us/community-repository/moderation/package-verifier/) · [push command](https://docs.chocolatey.org/en-us/create/commands/push/)

## Windows compatibility and clean-install gate

- Record ContextPick's actual minimum Windows version, supported architectures, install scope and prerequisites from its release configuration. Compare these with each distributor's documented test environment before submission. WinGet documents clean, unattended installation validation, but its public validation docs do not specify a fixed Windows build or timeout; record the environment and result from the actual PR checks/logs rather than assuming one. Chocolatey's published verifier profile lists Windows Server 2019, WSL, .NET 3.5/4.8, updates through 2024-05-28 and a 20-minute limit per install/uninstall command; confirm the actual image and current limits before submission. Do not lower ContextPick's supported OS floor to match a distributor test image. Follow the channel's documented review path for incompatibilities: Chocolatey directs verifier exemption requests to site admins on the package page; WinGet does not document a general environment-bypass, so use the applicable PR/admin-review process and leave the channel blocked if there is no supported resolution. Track any decision and test on ContextPick's supported Windows versions. Recheck [WinGet validation](https://github.com/microsoft/winget-pkgs/blob/master/doc/Validation.md), its [failure-review guidance](https://github.com/microsoft/winget-pkgs/blob/master/doc/ValidationFailureGuide.md), and the [Chocolatey verifier specification](https://docs.chocolatey.org/en-us/community-repository/moderation/package-verifier/) before each submission.
- Use disposable, restored clean environments with no previous ContextPick install, downloaded app dependencies, setup caches or developer tools that could satisfy prerequisites. Run direct-installer and package-manager paths independently, including the package manager's actual install command. Test unattended install, upgrade, uninstall, install registration and cleanup, supported standard-user/elevated contexts, install locations and permissions. Check every declared prerequisite and installer side effect. For Tauri Windows bundles, verify whether the chosen bundle detects or provisions WebView2 and test first install with a clean machine plus the relevant online/restricted-network condition; do not assume the runtime is present. Include offline testing only where the installer claims offline operation. [Tauri Windows installer and WebView2 options](https://tauri.app/distribute/windows-installer/)
- Choose images from ContextPick's supported OS range and the real distributor environments. At M5.5, use clean snapshots for local candidates and package definitions; never let one test seed another. At M5.6, retain the external verifier/moderator results and repeat the install through the accepted public feed. If a test fails, capture the full log and moderation feedback, classify artifact/installer, environment, metadata or policy causes, and reproduce on a comparable image where feasible. Correct the package or artifact, or pursue a channel-specific administrator review/exception where documented; do not presume a general waiver exists. If binary bytes change, publish a new immutable asset and follow that channel's resubmission/version rules. Resubmit or request re-verification through that channel and confirm its final accepted state. Do not replace published bytes in place, bump versions unnecessarily or infer acceptance from a green release workflow.

## Homebrew Cask (official macOS cask tap)

Homebrew is the recommended free macOS package-manager route for this desktop app. The official `homebrew/cask` tap is more discoverable, but admission is subject to its public-interest policy.

- **Artifact:** Casks distribute upstream-built macOS apps/installers. Provide a downloadable `.dmg`, `.zip`, `.pkg`, or other supported archive containing the app; a `pkg` installation needs an explicit `uninstall` stanza. The Cask uses a unique token/filename and structured Ruby DSL. [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook) · [acceptable casks](https://docs.brew.sh/Acceptable-Casks)
- **Cask metadata:** Required stanzas are `version`, `sha256`, `url`, `name`, `desc`, and `homepage`, plus the applicable artifact stanza such as `app` or `pkg`. Use a concrete version and exact SHA-256 for stable releases. `:latest`/`:no_check` are supported special values but weaken pinning and should not be selected without an explicit update/integrity rationale. Use `livecheck` where version discovery is non-obvious; provide architecture-specific URLs/checksums only if upstream actually publishes distinct artifacts. [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook)
- **Hosting and integrity:** The URL must deliver a release published by ContextPick or a distribution source the project publicly endorses; hidden/account-gated downloads and unendorsed mirrors are not acceptable. Keep a stable, publicly reachable release URL for each version and verify that its bytes match the cask SHA-256. Homebrew’s cask repository retains the formula metadata, not an uploaded app binary. [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks) · [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook)
- **Signing/notarization:** Homebrew’s cask acceptance policy requires macOS executable artifacts assessable by Gatekeeper to pass Homebrew’s Gatekeeper checks on a default macOS configuration; users’ Gatekeeper protections must not be disabled or bypassed. Homebrew applies quarantine and delegates those checks to macOS. Separately, Apple says apps distributed outside the Mac App Store are checked for Developer ID signing and, by default on current macOS, notarization. Plan a Developer ID signed and notarized app/package (and staple where supported), then verify on a clean supported Mac; this is the practical route to satisfy both Gatekeeper and friction-free installs. Treat Homebrew Gatekeeper acceptance as repository policy and signing/notarization as Apple platform behavior, not a Homebrew claim that notarization certifies safety. [Homebrew security model](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain) · [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks) · [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) · [Apple safe app guidance](https://support.apple.com/en-us/102445)
- **Submission and maintenance:** Read the acceptance policies, run applicable local cask audit/tests, fork `Homebrew/homebrew-cask`, and open a PR; official-tap changes are human reviewed. Treat a merged PR and published cask as acceptance, then verify installation from the official tap on a clean supported Mac; an open PR or local audit is not availability. The shared policy currently expects public interest beyond the author (normally at least 30 forks, 30 watchers, or 75 stars; for a repository-owner self-submission, 90 forks, 90 watchers, or 225 stars), with exceptions at maintainers’ discretion. A live repository check on 2026-10-09 found 0 stars, 0 forks and 0 watchers, below the normal thresholds; do not assume an official cask PR will be accepted yet. A project-maintained third-party tap is a free fallback, but Homebrew treats third-party taps as unsupported code that requires explicit trust, so document that install step and limitation. A new cask creates ongoing maintenance obligations: keep versions/checksums/downloads current, respond to CI/review, and maintain a working supported macOS artifact. [Package acceptance policy](https://docs.brew.sh/Package-Acceptance-Policy) · [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks) · [open a Homebrew PR](https://docs.brew.sh/How-To-Open-a-Homebrew-Pull-Request) · [Homebrew security/review](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain)

## Release evidence and completion

| Stage | Evidence required |
|---|---|
| Installer built | Versioned artifact, target OS/architecture and successful build result. |
| Installer validated locally | Clean-machine direct installation with logs; prerequisites, unattended behavior, upgrade and uninstall verified. |
| Package candidate generated and validated | Package ID/version and definition generated; metadata/schema/package-script checks pass; installation from a local package source or manifest is recorded. |
| GitHub Release published | Public, version-specific artifact URL and SHA-256; do not replace bytes at that URL. |
| Public asset validated | Download the published URL and confirm HTTPS reachability and exact hash against the release candidate. |
| Submitted | Package ID/token and version plus the WinGet PR, Chocolatey moderation page or Homebrew PR/tap reference. |
| External verification | Record repository installer/package checks as passed, failed or pending; link the results and any formal verifier exemption. |
| Accepted and published | WinGet PR merged and package published, Chocolatey package **Approved**, or official cask PR merged and published. A third-party tap is tracked separately; validation passing alone is not acceptance. |
| Available to users | Install the accepted version using the normal public package-manager command on a clean supported machine; record the result and confirm launch/uninstall. |

Keep this record per channel and version: package ID/token; immutable release URL and SHA-256; submission/moderation URL; automated and human review results; accepted/public version or exact outstanding blocker, owner and next action; clean end-user install evidence; maintainer for updates and review responses. A pending external decision may be documented as a blocker, but the channel is not available until acceptance and public-feed installation are confirmed.

## Roadmap mapping

The execution checklist remains in [ROADMAP](ROADMAP.md). M5.5 covers unpublished candidate bundles, clean local installation evidence and generated/static/local validation of package definitions. M5.6 covers immutable public release URLs, exact remote-asset validation, completed initial submissions, external verification, repository acceptance and end-user installation. Record any external blocker with its owner and next action, but leave M5.6 and distribution-complete status open while a required acceptance or public-feed install is pending. Submission, verification and acceptance are distinct states; a pending decision must not be reported as an accepted or available channel. Package-manager PRs/submissions are separate external publications; only the Windows GitHub release was explicitly authorized on 2026-10-09.

For the generated Windows bundle, verify its installer type, architecture, scope, silent and silent-with-progress switches, WebView2 bootstrapper, upgrade/uninstall behavior and ARP identity. Confirm Authenticode status from the actual artifact. The Chocolatey package must have checksum-enforcing download scripts and valid metadata; if it embeds binaries, include recognized verification/license files and establish redistribution rights. For macOS, test the actual app/archive/installer and uninstall behavior on a supported Mac, check Gatekeeper on a default configuration, and record Developer ID signing/notarization. Validate manifests locally in M5.5, then against exact public HTTPS assets in M5.6. Keep API keys and signing credentials in authorized secret storage and document channel ownership, update monitoring, review response and package withdrawal.
